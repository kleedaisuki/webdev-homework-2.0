# 星河工坊 · 需求文档

**世界杯专题站与团队主页** · 互联网数据库开发 · 团队课程设计

版本 1.0 ｜ 2026-11-13 ｜ 本地演示交付

## 1 问题与目标

课程要求每组交付一个含前台展示与后台管理的团队主页。本组把交付载体定为**世界杯专题站 + 团队主页**：两个入口、同一套业务数据库。专题站承担内容主体（赛事、赛果、球队、球场），团队主页承担团队自身的展示（成员、分工、交付物下载），访客留言把两者串成一条可审核的互动链路。

要解决的三个具体问题：

1. 赛程与赛果散落在网页表格与聊天截图里，无法按阶段、日期、球队检索，也无法区分"未开赛"与"0:0"。
2. 团队过程材料（需求、设计、手册、演示脚本）与个人作业分散在各人电脑，助教验收时要逐人索要。
3. 访客反馈只能发在群里，既没有留痕也没有审核，无法作为"前后台真实读写同一业务库"的证据。

因此交付重点是三件事：**前后台读写同一业务数据库**、**超过十张有业务含义的表**、**能在一台干净机器上重建并演示**。

## 2 角色与权限边界

| 角色 | 目标 | 允许行为与限制 |
|---|---|---|
| 访客 | 看比赛、看团队、留言 | 浏览已发布的赛事、球队、成员与交付物；提交留言并进入待审核；不能进入后台，改 URL 也拿不到权限 |
| 成员 | 维护本组资料 | 登录后可编辑被授权的团队与成员资料；不能审核留言，不能发布赛事 |
| 管理员 | 发布内容、审核留言 | 管理团队、成员与外部链接；创建并发布赛事，录入赛果；审核或拒绝留言；所有写操作留痕 |

权限判定在服务端完成（控制器过滤器 + `account.role` 字段），前端隐藏菜单不构成授权。

### 3.2 功能需求与验收

| 编号 | 功能 | 可观察的验收结果 |
|---|---|---|
| R01 | 查询赛程与赛果 | 列表可按阶段、日期、球队筛选，按开赛时间排序；已完赛显示比分；未开赛比分显示"—"而不是 0:0；草稿赛事不出现在列表，直接访问其详情返回 404 |
| R02 | 后台发布演示赛果 | 草稿 → 发布 → 录入比分三步走通；标记完赛必须给出两个非负整数，0:0 合法；未开赛不允许填比分；发布后前台刷新即可见；每次修改刷新更新时间 |
| R03 | 浏览团队与成员 | 首页与 `/team` 展示团队简介与成员卡片；成员详情显示分工、负责 Issue 与外部链接；只有 `published` 内容公开，草稿访问 404；中文正常显示 |
| R04 | 后台编辑课设资料 | 可修改团队简介、成员信息与外部链接；保存后前台刷新可见；必填、长度与关联校验生效，非法提交不会让数据库进入半完成状态 |
| R05 | 留言及审核 | 无需登录即可提交合法留言，提交成功页面明确显示"待审核"，不把提交成功误当公开发布；只有审核通过的留言出现在公开列表；后台可通过或拒绝并填写备注；每次审核写入 `guest_review` 并记录审核人 |
| R06 | 两类作业下载 | `/downloads` 分「团队交付物」与「个人作业」两栏，团队 6 项、每人 3 份；点击返回可正常打开的文件；文件名遵循课程命名约定 |

## 4 数据需求

### 4.1 业务表清单（11 张）

| 表名 | 中文名 | 用途 | 关键约束 |
|---|---|---|---|
| `account` | 后台账号 | 登录与权限 | 用户名唯一；密码存单向哈希，不存明文；`role` 区分成员与管理员 |
| `project_team` | 团队主体 | 队名、简介、封面、协作说明 | `publish_status` 取 `draft`/`published` |
| `project_member` | 团队成员 | 姓名、学号、组内分工、技能、简介 | 属于某团队；`sort_order` 控制展示顺序 |
| `member_link` | 成员外链 | 成员的个人主页、博客等 | 外键指向成员，删除成员时级联 |
| `project_team_link` | 团队外链 | 仓库地址、看板地址、演示地址 | 外键指向团队 |
| `tournament` | 赛事届次 | 赛事名称、年份、赛制说明 | 默认收录一届精选小组赛；`publish_status` 同上 |
| `national_team` | 国家队 | 名称、三字代码、所属洲、旗帜 | 代码唯一，供筛选与展示 |
| `venue` | 球场 | 名称、城市、国家、容量 | 容量为非负整数 |
| `fixture` | 赛程赛果 | 届次、主客队、球场、开赛时间、阶段、比分、状态 | 主客队各为 `national_team` 外键且不相等；`status` 取 `scheduled`/`finished` |
| `guest_message` | 访客留言 | 昵称、联系方式（可选）、正文、状态 | `status` 取 `pending`/`approved`/`rejected`；正文长度受限 |
| `guest_review` | 审核记录 | 审核人、结果、备注、时间 | 外键指向留言与账号；一条留言可多条记录，以最新为准 |

### 4.2 主要关联

- 团队 1—n 成员（`project_member.team_id`），团队 1—n 团队外链。
- 成员 1—n 成员外链（`member_link.member_id`）。
- 届次 1—n 赛程（`fixture.tournament_id`）；球场 1—n 赛程（`fixture.venue_id`）。
- 国家队 1—n 赛程，**通过两个外键**（主队、客队）建立，而不是把队名存成字符串。
- 留言 1—n 审核记录（`guest_review.message_id`）；账号 1—n 审核记录。

用外键而非逗号拼接字符串，是为了保证"同一支球队只有一个名字"，并让"按球队筛选赛程"成为一次连表查询。

### 4.3 状态与取值约定

| 字段 | 取值 | 含义 |
|---|---|---|
| `fixture.status` | `scheduled` | 未开赛，比分字段必须为空 |
| | `finished` | 已完赛，比分必须为两个非负整数 |
| 团队与成员的 `publish_status` | `draft` / `published` | 草稿仅后台可见 |
| `guest_message.status` | `pending` / `approved` / `rejected` | 待审核 / 已通过 / 已拒绝 |
| `guest_review.result` | `approved` / `rejected` | 与留言状态联动 |

### 4.4 数据质量约定

- **未开赛的比分是空值（NULL），不是 0:0。** 0:0 是"踢完且互交白卷"，两者在展示与统计上必须区分。
- 演示数据统一打标记并在页面标注"演示"，不冒充真实赛果；正式样本注明来源（如 FIFA 官方赛程页）。
- 表字符集统一 `utf8mb4`，时区统一 Asia/Shanghai，避免中文队名与时间显示错乱。
- 设计文档附数据库字典；`data/schema.sql` 为结构定义，`data/install.sql` 为可从空库重建的同结构还原文件。

## 5 非功能需求

**安全**：服务端校验、输出转义、参数化查询；所有写操作使用 POST 并启用 CSRF 防护；密码单向哈希；后台权限在服务端校验，隐藏入口不等于授权。

**兼容性**：面向桌面与移动端现代浏览器，采用服务端渲染，不依赖前端单页应用；中文字体与姓名正常显示。

**可维护性**：遵循模型-视图-控制器分层，业务约束写在模型与数据库，视图只负责呈现；自编 PHP 文件带英文注释头；命名统一，一个功能一个文件，避免巨型控制器。

**性能**：课程数据量下浏览、筛选、表单、图形均可即时响应；列表查询有明确排序与数量上限，不承诺未经测量的吞吐量。

**部署边界**：默认只绑定 `127.0.0.1`，MySQL 不对外开放端口。这是课程本地演示配置，不是公网生产方案。

## 6 协作与范围控制

### 6.1 版本控制与任务流程

- 工具：Git 版本控制，GitHub 托管，Issues 定义任务，Projects 看板跟踪状态。
- 一条 Issue 只指派一人、只开一个分支、只提一个 Pull Request；PR 正文写 `Closes #实际Issue号`，并附改动目录、所属 M/V/C 文件路径与可复现的验收步骤。
- 合并前由组长评审；合并采用压缩合并，保持主干历史线性；每日先合并当天可验收的 PR，再开工新任务。
- 分支按 `feat/`、`docs/` 前缀命名并带 Issue 编号；不提交 `vendor/`、`config/db.php` 与运行时目录。

### 7.2 一致性检查

代码、SQL 与 PDF 三者描述一致：路由与文档一致，表名与字典一致，截图与实际页面一致。演示使用两个浏览器会话分别扮演访客与管理员，验证"提交留言 → 后台审核 → 前台可见"的完整链路。

### 7.3 已知边界

- 开发周期一周，数据范围为一届精选小组赛；不追求赛事全覆盖。
- 赛果非实时，由后台手工录入，演示数据与正式样本分开标注。
- 站点仅本地运行，不承诺公网可用性与并发能力。
